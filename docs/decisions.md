# 用户决策

## U-01 — 在 fork 内采用提案流程

- Source: 2026-11-20，用户在讨论 `project-docs` L3、长期保留 `develop` 和从 `upstream/main` 创建投稿分支后确认「那我懂了，就这么来配置吧」。
- Supersedes: none
- Superseded by: none

在 fork 中采用 L3 提案流程。长期在 `develop` 版本化维护 `docs/`，包括已归档的提案。
`main` 跟随上游。投稿时从 `upstream/main` 创建 PR 分支，带上对应的代码、测试和适合上游的文档。
个人笔记和过程记录放在 `.local/`，用本地 Git 排除规则忽略。

## U-08 — 官方参考装配的分批验收

- Source: 2026-11-22，用户要求「批量 SDK 检查和真实代理采用率各自验收」，随后明确「轮组首批通过后，按同一提案批量展开」「常规扩展无需逐件另开提案」及「整体验收还要求交付官方组合条目的全量筛查报告，并在至少一个机制不同的接口族上实际跑通同一流程」。
- Supersedes: none
- Superseded by: none

[P-007](proposals/archive/P-007-official-reference-assemblies.md) 首批验收覆盖轮组的共性问题发现、批量修正和回归。随后全量筛查冻结发布版中的官方组合条目，按接口族报告分母、通过数、失败和未覆盖原因。已有可靠判据的族直接批跑，需专门判据的族分别补充；每次修正后重跑全部已覆盖样本和误接反例。整体验收须在另一种装配机制实际跑通。SDK 批量检查与 [U-05](#u-05--连接放置的配对验收) 的真实代理采用率分别验收。

## U-09 — 有证据的装饰接口缺项可带限制放行

- Source: 2026-11-22，评审 P-004 时，针对「仅对规划中可简化的装饰接口允许带限制交付；必需连接必须实际接合」，用户确认「可以放行」。
- Supersedes: none
- Superseded by: none

若规划事先把装饰接口列为可简化，且能用两端实例、安装位姿和标准目录的复现证据解释该接口的数据缺项，可在交付报告中逐项列明限制后放行。记录内及标准目录重读的碰撞、悬空检查均须通过。必需连接须实际接合，原因未明的断开阻止交付。[P-004](proposals/P-004-flow-gates-and-records.md#整版结构检查)

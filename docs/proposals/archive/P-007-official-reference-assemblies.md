# P-007 — 基于官方参考装配的批量验证与成类修复

Status: completed

实现和验收结果见[官方装配实测](../../design/p007-official-assembly-evaluation.md)。

## 问题与目标

巴士的轮辋和轮胎在标准目录中都有端点。P-001 能给出候选，却把每个试装都判为碰撞。单独为巴士移动端点，无法回答同一供体还影响哪些轮组，也无法判断改动是否让装反的轮胎通过。LDraw 官方组合文件留下了原作者使用的零件、位置和方向，可以用来复现这类问题。一个文件也可能只描述贴纸或几个共同出现的零件，只有能说明**哪两个实例应在何处以何种方式接合**时，才有连接正例。

本提案先在轮组上走通“提取参考 → 识别共同原因 → 修正 → 全组回归”，再筛查冻结版全部官方组合条目，实际覆盖另一种装配机制。下面的数字是草案阶段的只读复核，姿态恢复率、误接率及修正后的结果留待实施验收。

## 来源、样本和分母

- **发布范围。** 用 P-003 的 `scan_snapshot(root).verify()` 核对 LDraw 2026-10 的零件及几何依赖指纹。全量入口取冻结目录中 `kind == assembly` 与官方头部类型首词为 `Shortcut` 的并集，按顶层 ID 去重。目录有 5,164 个 assembly，另有 152 个移号、5 个别名和 1 个贴纸条目带 Shortcut 标记，共 **5,322 个待筛条目**。这是清单计数；各接口族的可验证比例须从全量筛查得到。[快照指纹与条目分类](../../../packages/bricklayer/src/bricklayer/ldraw/scripts/official_snapshot.py) · [冻结目录](../../../packages/bricklayer/src/bricklayer/ldraw/official_catalog_2026-10.json)
- **装配证据。** 从原文件逐行保留 type-1 引用的实例、颜色、平移（LDU）和 3×3 变换。有嵌套时沿实例路径复合变换，保留文件、行号、发布版、原文件 SHA-256、作者及许可。对选定的宿主 H 和子件 C 保存相对位姿 `inverse(T_H) × T_C`。P-003 的组件 ID 列表可用于发现条目，逐实例的顺序、重复出现和位姿从原文件恢复。
- **进入正例的依据。** 每族记下角色、方向、预期接口、相对姿态及依据，例如 Wheel 与 Tyre 组成的双件轮组，或有可辨认的轴与两半叶片的铰链。多件组合只为有装配依据的接口建样本，明确相邻但各接第三件的反例。贴纸与刚体同现、软管经过固件、纯几何子件及无法确定接口的共现均保留条目和原因。柔性件待有形态、端部和约束判据时单列。非刚性矩阵、无法导入、依赖未解析分别记原因，禁止静默跳过。
- **计数。** 全量覆盖率按顶层条目统计，每个条目恰有一行。有多个接口时另列样本，标明已覆盖、部分覆盖或尚未验证，并保留每个未覆盖接口的原因。每族同时报来源条目数、接口实例数、唯一有序件号对数和负例数。别名、色变、印刷、左右手、同件对的不同装向保留独立来源，另按规范件号、相对姿态及几何/端点版本分组。只有证实等价才合并比较；同一件对的三个颜色变体不能充作三个独立根因。

## 每个样本的三项检查

| 检查 | 输入与方法 | 通过条件 |
| --- | --- | --- |
| 官方姿态 | 按原变换将两件放入标准 SDK，直接检查该对实例的配合及碰撞，保存命中的两端、接触位置和碰撞对。多件模型还要排除经第三件连通的情况。 | 预期接口被识别，同时该对无碰撞。分别保留两个布尔值。 |
| 候选恢复 | 保留宿主位姿，只给子件和目标旋转。用 P-001 默认查询上限 20 和试装上限 8，保持返回次序；不给目标平移、官方 mounting 或文件专用提示。 | 预算内有通过试装的候选，且命中预期接口，宿主局部坐标下的平移和旋转与参考等价。记录首个命中排名、位姿误差、仅有非等价通过、零候选、全部试装失败及其原因。扩预算只用于定位。 |
| 错误姿态 | 每个正例关联至少一个有独立依据的负例，例如沿轴移出配合区、错到相邻孔或将有方向的非对称件反装。把变换固定在错误位置，同时检查直接配合和候选提交所认可的最终姿态。 | 该错误接口/位姿不能作为有效安装通过。返回另一处正确位置属于纠正，须报告实际落点。保存被拒阶段与证据，未构造可信负例的样本标记未验。 |

等价规则须在比较版本前按族冻结。先在宿主局部 LDraw 坐标求平移距离和相对旋转角，再对该件有来源依据的对称变换取最小误差。草案建议初始容差 0.1 LDU、0.1°，以原文件舍入回读和紧邻错误姿态作测试。轮胎绕轴的转动只有在该族的判据允许且无定向接口时才能忽略，端面互换、沿轴错位、左右手切换均需单独证据。铰链则保留给定的目标倾角与铰轴，不能因关节可转就接受所有角度。SDK 的碰撞与连接依然按其标准容差执行。[候选与试装 API](../../../packages/bricklayer/src/bricklayer/modeling/build.py)

## 首批轮组基线与复跑口径

以 `develop` 594effd、标准目录和冻结库复核。遍历官方顶层文件，取恰有两条直接 type-1 零件实例引用、两者均为顶层零件、子件描述规范化后分别以 `Wheel` 和 `Tyre` 开头的文件。规范化沿用目录去除前导标记（如 `~`、`=`）的规则。得到 **101** 个文件，均为 Shortcut，涉及 **98** 个有序件号对。原始 ID 对 3482/2346、7039/u9131、715/36 各出现两次。下表两行的分母均为 101。[名称规范化](../../../packages/bricklayer/src/bricklayer/ldraw/naming.py)

| 观测 | 逐文件互斥计数 |
| --- | --- |
| 按官方姿态直接放置 | 连通无碰撞 **63**，未连通无碰撞 **21**，连通且报碰撞 **10**，未连通且报碰撞 **7** |
| 以轮辋为宿主、给定轮胎朝向 | 至少一项试装通过 **66**，零候选 **19**，返回候选但试装全报碰撞 **16** |

**66 是有可行候选的文件数。** 这些候选尚未逐项比对官方等价位姿。此次也未建立轮组负例全集，两项均须在首次修正前补测并冻结。官方 `56904c01.dat` 的两条直接引用是 **56904 + 56898**，LDraw 原点和朝向重合。该姿态未连通、无碰撞，查询 4 个候选、4 次试装均报碰撞。OMR36 巴士用的是 **56904 + 30699**，复放该件对得到同类结果；它是另列的应用回归样例，不计入上述 101 个文件。两对是否同一根因有待验证。

按下列步骤可用现有 SDK 复核表中两行。运行环境使用仓库锁定依赖，`LDRAW_LIBRARY_PATH` 指向已核对的发布库根目录。清单指纹按小写文件名（含 .dat）排序，每行一个、末行带 LF，SHA-256 为 `81cb98b4ba602799af999c1e9c3357986cbb7b5a8ecc4e7c8d1651b3ceecf34e`。

1. 枚举并按上述规则筛文件，逐条保存 type-1 原文。在声明的库上用 `from_ldraw` 读两行，断言恰好导入两件，对照子件 ID 指定宿主 H、轮胎 C。按 `is_connected()` 与 `bool(colliding_placements)` 交叉计数。
2. 对每个文件新建空的 `LegoBuild`，执行以下查询。保存返回数、实际试装数、每项检查和诊断码。“全碰撞”仅指预算内实际试过的候选全因碰撞失败；未试的尾部单列。无候选、执行异常和混合拒因分别统计。
3. 对文件清单验指纹，汇总两张表并断言各自加总为 101。正式检查再对通过试装的位姿逐个做等价判定，并执行负例，将三项结果逐行关联到同一个样本。

```python
host = LegoBuild()
placed_rim = host.add_raw(rim.content, rim.pose)
candidates = host.find_connection_candidates(
    placed_rim, content=tyre.content, target_rotation=tyre.pose.rotation
)
trials = host.trial_connections(candidates)
```

## 从失败样本到成类修复

先按接口族、供体、变换、端点类型、碰撞体来源、失败阶段和件号对归组。相同诊断码只用来选取复核样本。选两个及以上不同装配，固定参考位姿，对照端点与碰撞几何，在测试分支只改变一个可疑因素。验证这一改动能解释同组的多个失败，并用未参与定位的同类样本（若有）和误接反例检验预测。优先处理能覆盖多个装配的共同来源。

| 区分原因的证据 | 拟修位置 |
| --- | --- |
| 端点供体缺失、选择了不同变体的供体，或供体自身的端点类型/位置错误 | 核实原供体与已知正确的同族装配，修源标注或供体选择，记录影响到的全部派生件 |
| 同源件的端点相对官方安装面出现一致偏差，供体局部端点正确，但映射到目标件后偏移 | 核对 P-003 记录的供体与坐标变换，在数据生成或补充数据源修正并重新生成 |
| 官方姿态的配合位置正确，凸体却在设计配合空间相交 | 对照原几何定位具体碰撞体，修改其生成或数据；保留真正穿透的负例 |
| 相对位置及方向正确，两种端点均存在却没有适用配合 | 用接口设计证据和不相容近邻验证类型与配合规则，再改规则 |
| 标准检查能识别官方姿态，求解结果偏移或正确候选落在预算外 | 分别检查目标旋转拟合、自由度、占用和排序，记录正确位姿第一次出现的排名 |

比较逐样本的修正前后矩阵，包括改善、持平、退步及原因。每次修正后重跑**所有已覆盖接口族的全部正例和误接反例**，保留失败明细及数据版本。逐件追加放行例外会留下同源错误，也削弱负例的区分力。无共同原因证据的个案保留为待查。

## 验收与展开顺序

### 第一步：轮组成类修正

交付可复跑的提取、检查和差分入口，保存发布库指纹、SDK 提交、数据指纹、判据版本、预算与执行命令。清单和逐项结果应能重建 101 个文件与 98 个件对的汇总。先把 66 个有候选通过的文件按等价命中与未命中分开，补齐每样本的误接反例，冻结修前结果。对同一输入重复运行应产生相同的样本 ID、排名、状态和汇总。

至少完成一项有共同根因的修正，使两个及以上独立装配在原预算内由失败转为相应项目通过，并展示根因、修正归属及逐案证据。以冻结的三项正式判据比较，全轮组原有通过项保持通过、负例零误接；所有剩余失败可从报告定位。“任意候选通过”作为诊断计数单列，修掉一个碰巧可行的错误位姿不能记为恢复率退步。

### 第二步：全量筛查与不同机制的实测

首批通过后统一扫描其余 **5,221** 个条目，与首批合成能和冻结清单对账的 **5,322 行**筛查报告。按接口分别标为**可直接验证、需要专门判定规则、目前缺少依据**，混合条目逐接口列出。对所有已有可靠判据的族直接批跑；第二类逐族补足正例依据、等价与误接规则后纳入同一流程；第三类记录缺失证据及再次纳入条件。别名与移号列出解析去向，未能识别任何接口的条目也占一行。

每族给出条目和样本分母、三项检查各自的通过/失败/未验数、逐阶段失败原因、未覆盖数及原因。负例另列总数与误接数。每项计数可回溯至条目或样本 ID，跨族条目在全量汇总中只计一次。筛查报告同时列规则版本与实际运行列表，便于检查所有可直接验证的族都跑过。

在**至少一个机制不同的接口族**（例如有目标倾角的铰链或有轴向插入深度的轴孔）实际走通提取、三项检查、失败归类、成类修正及跨族全量回归。报告记录该族判据如何区别于轮组，以及修正前后逐项结果。常规增加族、样本或判据在本提案持续登记。[验收边界](../../decisions.md#u-08--官方参考装配的分批验收)

## 取舍

全库任取两件枚举候选可以测搜索吞吐，却缺少判断安装是否正确的参照。只修 OMR 的三个现场实例能快速改善演示，却可能遗漏使用同一端点供体的其他装配。选用官方组合逐层展开，把归因成本集中在可复现、可成类修复的样本上。代价是要长期维护各接口族的安装判据、对称性和误接样本；报告保留缺少依据的条目，避免把易测族的通过率外推到整库。

## 与现有提案的交接

P-003 已完成冻结目录、能力说明和来源索引，P-007 复用这些事实，把确认的数据缺口送到相应生成层。P-001 继续负责代理查询、试装、执行诊断及 U-05 的原生代理配对验收。批量报告可给 P-001 提供最小复现和修复前后原因码。P-004 的标准目录重读可引用同版本、同件对和匹配姿态的验证结果，差异或未知断开仍需在现场解释。官方参考与负例检验 SDK 对装配的判断，真实代理采用率仍由相同任务、模型及预算下的成品计量决定。[P-003](P-003-official-part-coverage.md) · [P-001](../P-001-connection-driven-building.md) · [P-004](../P-004-flow-gates-and-records.md)
